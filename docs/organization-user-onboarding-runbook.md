## Crear una organización

1. Abrir `/onboarding` y completar nombre de organización, nombre completo y correo. La contraseña se crea después de confirmar el correo.
2. El servidor guarda una solicitud pendiente con token aleatorio en hash y vencimiento de 24 horas. Todavía no crea usuario, organización ni membresía. La solicitud no almacena la contraseña.
3. Se envía un correo de confirmación. El enlace usa `AUTH_URL` o `NEXTAUTH_URL`; en producción se exige HTTPS. El token viaja en el fragmento `#` de la URL, que el navegador no incluye en la petición HTTP. La página lo retira de la barra de direcciones y declara la política meta `no-referrer`; luego consulta su vigencia mediante una acción POST. El proxy limita los POST a `/onboarding` a 10 por IP cada 15 minutos con un contador PostgreSQL compartido entre procesos. Requiere la migración de rate limit y `AUTH_SECRET` o `NEXTAUTH_SECRET`; si falta una IP válida, el secreto o la base, la solicitud responde 503. Nginx debe agregar la IP real del peer al final de `X-Forwarded-For` y la aplicación permanecer ligada a loopback. La aplicación añade un enfriamiento de un minuto por correo cuando conserva una solicitud tras aceptar el envío.
4. El destinatario abre `/onboarding/verify`, confirma el correo y crea una contraseña de al menos 12 caracteres y como máximo 72 bytes UTF-8. Ni la consulta inicial ni la acción de previsualización consumen el token; solo el envío explícito del formulario lo hace, por POST.
5. Una transacción vuelve a validar el token y que el correo siga libre, crea usuario, organización, membresía y auditoría, carga los datos sintéticos si se eligió el modo demo y elimina la solicitud pendiente. El token solo puede usarse una vez.
6. La interfaz muestra el mismo mensaje genérico para solicitudes aceptadas, correos ya registrados, reintentos recientes y fallos SMTP; no confirma el estado de la cuenta ni la entrega del correo. Si SMTP falla, se elimina la solicitud pendiente, no se crea ninguna cuenta ni espacio y no se muestra el enlace. Si no llega correo, se puede volver a solicitar el alta; el enfriamiento de un minuto aplica a una solicitud pendiente que ya se aceptó para envío.
7. Las solicitudes vencidas se eliminan al procesar un nuevo alta o un intento de confirmación. Además, programa a diario `/api/cron/cleanup-expired-organization-signups` con `CRON_SECRET`; devuelve el número de solicitudes y buckets de rate limit eliminados. El ejemplo está en [deploy.md](deploy.md), pero el cron no está instalado ni verificado en el entorno objetivo.

Una cuenta existente y autenticada sin organización puede crear su espacio directamente. Una cuenta que ya pertenece a otra organización no puede crear una segunda membresía con el modelo actual. El alta pública usa una respuesta genérica para no revelar por el contenido de la respuesta si un correo ya tiene cuenta, si SMTP falló o si la solicitud quedó en enfriamiento. No se afirma resistencia a análisis temporal: el envío SMTP es síncrono y el tiempo de respuesta puede variar. Esto tampoco oculta el hecho de la entrega a quien controla el buzón.

Tras el primer acceso, el dashboard vacío guía al usuario por la preparación del espacio, la invitación del equipo según sus permisos y el registro del primer candidato. El enlace de equipo apunta a **Ajustes → Usuarios**; la tarjeta de personalización es opcional. Al crear el perfil, la siguiente tarea documental se abre desde el propio candidato.

## Invitar usuarios

1. Un usuario con rol autorizado abre **Ajustes → Usuarios** y elige **Invitar usuario**.
2. Escribe nombre, correo y rol permitido. El servidor vuelve a comprobar permisos, organización, estado de cuenta y límite del plan.
3. El servidor crea una invitación de siete días y envía un enlace de un solo uso. El token se guarda como hash y el acceso aún no está concedido. Si ya existe una invitación pendiente al mismo correo, solo se puede rotar y reenviar una vez por minuto; la comprobación usa `updatedAt` dentro de la transacción para que también aplique entre procesos.
4. Una persona sin cuenta abre el enlace y establece una contraseña de al menos 12 caracteres y como máximo 72 bytes UTF-8; la aceptación verifica el correo de esa cuenta. Una cuenta existente debe iniciar sesión con el correo invitado y volver a abrir el enlace.
5. La aceptación crea o reactiva la membresía y registra el evento de auditoría dentro de la transacción. La invitación no puede aceptarse por segunda vez.

Las plazas reservadas por invitaciones pendientes cuentan contra el límite de usuarios. Reenviar al mismo correo, una vez transcurrido el enfriamiento, reemplaza el token anterior, por lo que el enlace anterior deja de funcionar. Si el proveedor informa un fallo de envío o lanza un error, Ajustes muestra el enlace una sola vez para compartirlo por un canal seguro y el servidor registra un aviso sin incluir el destinatario ni el enlace. No se comunica ninguna contraseña temporal.

## Retirar acceso

Desde Ajustes, un administrador puede desactivar la membresía de un usuario activo. Para invalidar un enlace pendiente, el administrador puede enviar una nueva invitación a esa misma dirección; el token anterior queda reemplazado. La administración de varias organizaciones por cuenta no está habilitada.

## Antes de usar este flujo en un entorno

- Ejecutar y registrar cada escenario de la [matriz P4-04](p4-04-onboarding-acceptance-matrix.md) en una misma imagen y entorno aprobados. La matriz separa cobertura de la imagen anterior de los casos no repetidos en el candidato actual; sigue siendo una hoja pendiente, no evidencia de aprobación.
- Aplicar las migraciones `20261010130000_organization_invitations`, `20261017170000_pending_organization_signups` y `20261018110000_shared_rate_limit_buckets` mediante el procedimiento normal del entorno objetivo y desplegar la versión que contiene los modelos. Las nuevas migraciones siguen pendientes; producción no ha cambiado.
- Confirmar que `AUTH_URL` o `NEXTAUTH_URL` apunta al dominio público correcto y que SMTP entrega los mensajes y enlaces.
- El límite por IP en `src/proxy.ts` usa PostgreSQL compartido y requiere `AUTH_SECRET` o `NEXTAUTH_SECRET` para generar HMACs; si no hay secreto, una IP válida o el almacén, las rutas protegidas responden 503. Validar en el release que Nginx sobrescribe/agrega `X-Forwarded-For` como en [deploy.md](deploy.md), aplicar la migración y probar concurrencia desde más de un proceso antes de abrir autoservicio.
- Repetir en la candidata actual todos los casos O-01–O-30, en particular: no hay usuario/organización antes del clic de confirmación, no se almacena contraseña pendiente, la respuesta no permite enumerar cuentas por contenido, el token no aparece en URL/logs, password mismatch, consumo único, expiración y reenvío, enfriamiento de invitaciones, alta en modo demo y caída SMTP sin alta parcial. Incluir los nuevos casos de idioma de interfaz/correo y diagnóstico de fallos sin datos personales.
- La evidencia E2E de diez comprobaciones mencionada en documentos anteriores corresponde a una imagen distinta. No se da por aprobada aquí ninguna aserción sin registro individual sobre el mismo release y entorno.
- El proveedor transaccional actual es SMTP síncrono, sin cola durable ni proveedor secundario. Si SMTP no está configurado o falla, el alta pública no crea usuario ni tenant y el formulario muestra la respuesta genérica; el timeout evita esperas largas, pero no garantiza entrega ni detecta rebotes.
- `npm run check:smtp -- recipient@dominio` envía un mensaje real de prueba. Ejecutarlo solo con un buzón controlado y después de configurar el proveedor; un resultado exitoso acredita aceptación SMTP de ese mensaje, no su llegada a la bandeja ni la entrega futura.
- No usar el flujo como aceptación de términos: P4-03 sigue pendiente y su aceptación/versionado debe resolverse allí antes de onboarding contractual.
